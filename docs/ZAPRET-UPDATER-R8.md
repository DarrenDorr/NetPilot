# Zapret Updater R8 — транзакционная установка и rollback

## Назначение

R8 добавляет файловую транзакцию установки проверенного пакета Zapret. Он работает поверх R6/R7: пакет уже должен происходить из официального immutable-релиза, пройти ограничения загрузки, SHA-256, безопасную распаковку и проверку структуры.

R8 всё ещё не открывает `UpdateApply` через IPC. Сначала транзакция должна пройти автоматические проверки как самостоятельный слой.

## Каталоги Windows

Базовый защищённый каталог установленной версии:

```text
%ProgramFiles%\NetPilot\Engines\Zapret
```

Внутри используются обычные реальные каталоги:

```text
current\            активная версия
previous\           предыдущая версия для быстрого отката
.rollback-pending\  только временный слот незавершённой транзакции
.staging\           будущий защищённый staging
```

Junction, symlink и другие reparse point не используются.

## Manifest установленной версии

В каждый пакет перед переводом в `current` NetPilot добавляет собственный:

```text
.netpilot-engine.json
```

Manifest содержит:

- версию схемы;
- upstream ID;
- версию Flowseal;
- SHA-256 исходного официального ZIP;
- время установки UTC.

Неизвестная схема, неизвестный upstream, повреждённый digest или слишком большой manifest отклоняются.

Если входящий upstream-пакет уже содержит файл с зарезервированным именем `.netpilot-engine.json`, установка прекращается — NetPilot не позволяет пакету подменить собственную metadata.

## Запрет downgrade

Перед обновлением читается manifest текущего `current`.

Обычная операция Apply разрешает только:

```text
target version > installed version
```

Равная версия возвращает `VersionAlreadyInstalled`.

Меньшая версия возвращает `DowngradeRejected`.

Rollback является отдельной явной операцией и поэтому может вернуть предыдущую версию.

## Транзакция обновления

Для существующей установки схема:

```text
1. проверить incoming package
2. добавить manifest
3. current -> .rollback-pending
4. incoming -> current
5. повторно проверить current + manifest
6. старый previous безопасно удалить
7. .rollback-pending -> previous
```

Все `Directory.Move` выполняются на одном томе. Если staging находится на другом томе, операция отклоняется с `StagingVolumeMismatch`.

Это необходимо для предсказуемой семантики переименования каталогов и уменьшения окна частично скопированных файлов.

## Автоматическое восстановление после ошибки

Если после перемещения старого `current` дальнейшая операция завершается ошибкой:

- новый неполный `current` удаляется только после проверки, что путь находится внутри engine root и не содержит reparse point;
- `.rollback-pending` возвращается в `current`.

Если автоматическое восстановление само не удалось, возвращается отдельная ошибка `RollbackRestoreFailed`. Она не маскирует ситуацию как успешное обновление.

## Восстановление после аварийного завершения процесса

Перед новой файловой транзакцией вызывается `RecoverPendingTransaction()`.

Если существует `.rollback-pending`, а `current` отсутствует:

```text
.rollback-pending -> current
```

Если существуют и `.rollback-pending`, и `current`:

- новый `current` полностью проверяется;
- проверяется его NetPilot manifest;
- при успешной проверке транзакция считается дошедшей до нового `current`, а старый pending становится `previous`;
- при провале проверки новый `current` безопасно удаляется, а pending восстанавливается как `current`.

Таким образом незавершённое обновление после сбоя питания или завершения процесса не должно оставлять систему в неопределённом состоянии без попытки безопасного восстановления.

## Явный rollback

При наличии `current` и `previous` операция rollback меняет их местами через `.rollback-pending`.

После успешного отката прежний `current` становится `previous`, поэтому пользователь сможет отменить откат повторной безопасной операцией после отдельного UI/IPC слоя.

## Защита файловых операций

Перед рекурсивным удалением NetPilot:

- канонизирует путь;
- проверяет, что он является дочерним каталогом фиксированного engine root;
- проверяет всё дерево на отсутствие reparse point.

Произвольный путь пользователя в эти операции не передаётся.

## Что ещё не включено

R8 не включает:

- IPC `UpdateApply`;
- IPC `EngineInstall`;
- IPC `EngineRepair`;
- UI-кнопку обновления;
- автоматическое обновление;
- постоянный архив системных backup в `%ProgramData%\NetPilot\SystemBackups`;
- восстановление пользовательских настроек поверх нового пакета;
- установщик Windows и финальные ACL Program Files.

`previous` — защищённый быстрый rollback-slot самого движка, а не пользовательская резервная копия.

## Следующий этап

После прохождения CI/Windows/CodeQL R8 следующий слой должен:

1. собрать R6 + R7 + R8 в единый `ZapretUpdateOrchestrator`;
2. использовать фиксированные Windows staging paths;
3. требовать остановки активного `winws` перед переключением;
4. подключить только одну высокоуровневую IPC-команду проверки/применения обновления;
5. разделить `CheckUpdate` (непривилегированная metadata) и `ApplyUpdate` (служба);
6. добавить user confirmation на уровне UI до `ApplyUpdate`;
7. затем реализовать системные backup/retention и repair.
