# R19 — диагностически осознанная автоматика

## Статус

R19 добавляет в автоматический подбор профиля отдельный этап принятия решения: **нужно ли вообще пытаться менять сетевой профиль при текущей причине сбоя**.

До R19 после подтверждённой недоступности ресурса selector мог перейти к проверке альтернатив независимо от диагностического кода. Это было безопасно с точки зрения ограничения количества кандидатов и восстановления исходного профиля, но логически неверно: например, смена DPI-профиля не должна использоваться как универсальное средство для DNS-ошибки, отклонённого endpoint или ответа HTTP 5xx.

R19 исправляет это fail-closed.

## Основное правило

Альтернативные профили разрешено автоматически проверять только при явно допущенных классах сетевого сбоя.

На текущем этапе allowlist содержит:

- `TcpConnectFailed`;
- `TlsHandshakeFailed`;
- `Timeout`.

Этот список намеренно мал. Новый или неизвестный diagnostic code **не получает право на переключение автоматически**.

## Когда переключение запрещено

Automation не перебирает профили при следующих классах причин:

### DNS

`DnsResolutionFailed` → `RecoverySuppressedDnsFailure`.

DNS-проблема не считается достаточным основанием для смены DPI-профиля. Текущий профиль сохраняется.

### Ответ сервиса по HTTP/HTTPS

Коды вида `HttpXYZ`, а также `TooManyRedirects` и `RedirectWithoutLocation` → `RecoverySuppressedHttpResponse`.

Если сервер уже вернул HTTP-ответ или контролируемый redirect-результат, NetPilot не должен автоматически считать это доказательством того, что требуется смена сетевого профиля.

### Политика безопасности или конфигурация

`EndpointRejected` и `NoHealthEndpoints` → `RecoverySuppressedSecurityOrConfiguration`.

Automation не пытается обходить собственную политику безопасности переключением профилей.

### Неизвестная причина

Любой неизвестный, пустой или неподдерживаемый diagnostic code, а также промежуточные состояния `Unknown` / `Checking` → `RecoverySuppressedUnclassifiedFailure`.

Это ключевой fail-closed принцип R19: будущий новый код диагностики сам по себе не расширяет возможности Automation.

## Новый результат Automation

В `StrategySelectionStatus` добавлен статус:

`RecoveryNotApplicable`

Он означает:

1. проблема подтверждена;
2. исходный профиль известен и сохранён;
3. policy решила, что автоматический перебор профилей не применим;
4. ни один альтернативный профиль не активировался.

Это отличается от `NoWorkingAlternative`: при `NoWorkingAlternative` кандидаты могли реально проверяться, а при `RecoveryNotApplicable` их проверка намеренно не начинается.

## Подтверждение сбоя сохраняется

R19 не отменяет прежнее правило двухфазного подтверждения:

- первая проверка может быть временным сбоем;
- выполняется повторная проверка;
- если повторная проверка успешна, возвращается `TransientFailure` и профиль не меняется;
- только после устойчивого сбоя применяется `StrategyRecoveryPolicy`.

Таким образом, решение о смене профиля принимается только после подтверждения проблемы и проверки её класса.

## Отмена и восстановление исходного профиля

Прежняя failure-safe логика сохранена.

Если автоматический прогон уже активировал альтернативный профиль, а затем операция была отменена или прервана исключением, NetPilot пытается восстановить точный исходный профиль с `CancellationToken.None`.

Отдельный тест подтверждает последовательность:

`ALT11 → ALT12 → отмена → ALT11`.

R19 не ослабляет этот механизм.

## Пользовательский интерфейс

GUI теперь различает отказ от автоматической смены профиля и отсутствие рабочей альтернативы.

Для `RecoveryNotApplicable` пользователь получает понятное объяснение, например:

- проблема DNS — перебор профилей не выполнялся;
- сервис отвечает по HTTPS — автоматическая смена профиля не выполнялась;
- операция остановлена политикой безопасности или конфигурацией;
- причина недостаточно определена — текущий профиль сохранён.

Карточки сервисов также переводят безопасные diagnostic codes в человекочитаемые сообщения:

- проблема DNS;
- не удалось установить TCP-соединение;
- не удалось установить защищённое HTTPS-соединение;
- timeout;
- HTTP-код;
- отклонение endpoint политикой безопасности.

В интерфейс не передаются IP-адреса, URL проверки, exception message, содержимое HTTP-ответа или сетевой трафик.

## Что R19 не делает

R19:

- не добавляет packet capture;
- не читает пользовательский трафик;
- не добавляет proxy;
- не меняет DNS пользователя;
- не добавляет новые endpoint;
- не расширяет native capabilities;
- не включает `EngineInstall` или `EngineStart`;
- не делает BLOCK-компоненты допустимыми;
- не добавляет raw CLI, BAT, PowerShell или Lua;
- не меняет IPC v3.

## Security boundary

R19 работает только поверх нейтрального Automation/Health слоя.

Пока native admission не содержит ни одного `ADMIT`:

1. GUI использует `NoAdmittedEngineProfileRuntime`;
2. Service запрещает `EngineInstall` и `EngineStart`;
3. Updater не имеет admitted release;
4. R19 может классифицировать проблему и принять решение, но не получает обходного пути к native-коду.

## Следующий этап

После R19 можно развивать диагностику и UX независимо от native engine. Подключение реального Windows network engine остаётся заблокированным до появления нового исправленного tagged-кандидата и полного security admission со статусом `ADMIT`.
