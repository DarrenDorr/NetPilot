# Security Foundation R2

## Цель этапа

R2 усиливает локальную границу доверия между `NetPilot.App` и `NetPilot.Service` до подключения первых реальных привилегированных операций.

Главный принцип: идентичность клиента и сервера определяется средствами Windows и состоянием самого Named Pipe. SID, PID и Session ID не принимаются из JSON и не могут быть подменены полями пользовательского запроса.

## Проверка клиента службой

После подключения к Named Pipe служба получает:

1. PID процесса клиента через Windows API `GetNamedPipeClientProcessId`;
2. Session ID подключения через `GetNamedPipeClientSessionId`;
3. Session ID процесса через `ProcessIdToSessionId` и проверяет их совпадение;
4. Windows access token клиента через impersonation Named Pipe;
5. SID пользователя;
6. признак интерактивной пользовательской сессии;
7. уровень impersonation.

Соединение отклоняется, если:

- PID определить невозможно;
- Session ID процесса не совпадает с Session ID pipe;
- используется Session 0;
- токен не является интерактивным;
- клиент анонимный или гостевой;
- уровень impersonation недостаточен даже для идентификации;
- используется `LocalSystem`, `LocalService` или `NetworkService`;
- SID отсутствует или имеет недопустимый формат.

## Проверка службы клиентом

После подключения GUI не начинает обмен запросами сразу. Сначала он проверяет сервер Named Pipe:

1. получает PID сервера через `GetNamedPipeServerProcessId`;
2. получает Session ID сервера через `GetNamedPipeServerSessionId`;
3. требует Session ID `0`, то есть системную служебную сессию Windows;
4. читает владельца ACL Named Pipe;
5. требует владельца `LocalSystem`.

Это снижает риск подмены `NetPilot.Service` обычным пользовательским процессом, который заранее занял известное имя Named Pipe.

## ACL Named Pipe

- `NetworkSid` — полный запрет;
- `LocalSystem` — полный доступ;
- локальные администраторы — полный доступ;
- локальные аутентифицированные пользователи — только чтение/запись и чтение сведений безопасности, необходимых для проверки владельца канала.

Сам ACL не считается достаточной авторизацией. После ACL выполняется проверка SID/Session/токена.

## Межпользовательская изоляция

R2 не выдаёт службе право читать произвольные пользовательские данные. Установленный SID клиента становится контекстом авторизации будущей операции.

Любая будущая операция, которая затрагивает пользовательское состояние, обязана:

- использовать SID, полученный службой из Windows, а не из запроса;
- не возвращать данные другого SID;
- не принимать путь к пользовательскому профилю как доверенный ввод;
- самостоятельно проверять границы доступа перед выполнением.

## Что всё ещё отключено

В R2 реальные административные обработчики по-прежнему не выполняются. `OperationPolicy` работает по принципу `default deny`.

До отдельного аудита не включаются:

- установка движка;
- запуск/остановка движка;
- удаление/восстановление движка;
- применение обновления;
- восстановление резервной копии;
- другие операции, изменяющие состояние системы.

## Тестирование

Добавлен отдельный Windows test project и отдельный CI job на Windows.

Проверяются:

- нормальная интерактивная пользовательская идентичность;
- запрет Session 0 для GUI-клиента;
- несовпадение Session ID процесса и pipe;
- запрет `LocalSystem`, `LocalService`, `NetworkService` как пользовательского клиента;
- требование Session 0 и владельца `LocalSystem` для службы;
- получение реальной идентичности подключённого клиента из Named Pipe;
- отклонение обычного пользовательского процесса, который пытается выступать поддельной `NetPilot.Service`.

## Следующий этап

После успешного прохождения Windows CI, общих тестов и CodeQL можно переходить к первому движку. При этом первая реальная привилегированная операция должна получить собственный DTO, отдельную проверку параметров и отдельные отрицательные тесты.
