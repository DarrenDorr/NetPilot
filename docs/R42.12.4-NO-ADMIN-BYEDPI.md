# R42.12.4 — No-admin ByeDPI user-mode boundary

## Release goal

The first NetPilot runtime path uses reviewed ByeDPI 0.17.3 as a normal user process. The normal GUI path must not require elevation, a Windows service, WinDivert, transparent interception, or system-wide proxy mutation.

The reviewed candidate is pinned to:

- version: `0.17.3`
- file: `ciadpi.exe`
- size: `495685`
- SHA-256: `866e99c3c7690326cc6e365fe02980f06ae2b394c045555674fb95db52b0dbdd`

Any identity mismatch blocks launch.

## Least-privilege boundary

The primary GUI composition creates `WindowsByeDpiStrategyRuntime` directly in the user's process. It does not create `WindowsPrivilegedServiceClient` or `WindowsZapretStrategyRuntime`.

The user-mode installer:

- uses `PrivilegesRequired=lowest`;
- installs below the current user's LocalAppData Programs directory;
- does not register or control `NetPilot.Service`;
- does not invoke `sc.exe`;
- does not request `runas`;
- does not install or request WinDivert.

The existing service/Zapret path is retained only as an isolated legacy/experimental path. It is not admitted for the first ByeDPI release.

## Native process admission

Before each ByeDPI start, NetPilot:

1. requires the executable to remain inside the configured managed package root;
2. rejects reparse points in the package path and executable;
3. opens the executable without write/delete sharing;
4. verifies exact size and SHA-256;
5. keeps the verification handle open while the process is created;
6. launches only through `AuditedByeDpiUserModeProcessLauncher` using `UseShellExecute=false` and typed `ArgumentList` values.

The repository security policy allows `Process.Start` only inside explicitly audited launchers.

## Network boundary

ByeDPI is started as a SOCKS5 proxy bound only to `127.0.0.1` on a dynamically selected port.

The launch policy:

- passes `-i 127.0.0.1`;
- disables UDP association with `-U`;
- does not use `-N`, so hostname SOCKS5 requests remain valid;
- does not request transparent mode;
- does not request daemon/service mode;
- does not change the Windows system proxy;
- does not request WinDivert.

After start, NetPilot verifies both that the listener did not escape loopback and that it completes a SOCKS5 no-auth handshake before declaring the runtime running.

## Lifecycle containment

The ByeDPI child process is assigned to a Windows Job Object configured with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`.

Normal stop kills only the exact process object owned by the runtime and verifies that its listener disappears. Normal GUI disposal stops the owned runtime. If the GUI process terminates unexpectedly, closing the Job Object is intended to terminate the child process as well.

Failure to create/configure/assign the Job Object blocks runtime admission.

## Diagnostics and privacy

Support bundles remain local and are never uploaded automatically. Engine metadata scanning checks the application installation root first, with Program Files retained only as a legacy diagnostic scope. Absolute engine paths are not written into `engine-status.json`; only engine/version/architecture/relative executable/size/SHA-256 and a non-identifying scope label are recorded.

## Required evidence before release publication

R42.12.4 is not complete until all of the following pass:

1. normal CI, Windows security tests and CodeQL;
2. compilation and installation of the per-user installer;
3. execution under a deliberately created standard Windows user with a non-elevated token;
4. exact candidate SHA/size verification;
5. external HTTPS through the owned loopback SOCKS5 runtime;
6. process owner equals the standard test user;
7. no `NetPilot.Service` dependency or registration;
8. system proxy unchanged;
9. WinDivert state unchanged;
10. normal stop leaves no ciadpi/listener residue;
11. crash/owner-process termination proves Job Object cleanup;
12. the same no-UAC package passes on a physical Windows PC.

Until that evidence exists, `PRODUCTION_ADMISSION=BLOCK` and the reviewed ByeDPI Draft Release remains unpublished.

## Diagnostic pack when hosted Windows cannot launch the test user

The hosted workflow deliberately **remains failed** if its isolated standard-user process cannot start or the validator does not pass. A failed hosted run is never evidence of user-mode admission.

If the pack was successfully assembled, the workflow rechecks that the exact three-asset draft remains unpublished and unchanged. Only after that gate may it upload the short-retention **physical-PC validation pack** even though hosted validation failed. The pack manifest stays labeled `hosted_validation=NOT_YET_PROVEN` and `production_admission=BLOCK`. This is a local diagnostic test bundle, **not a release**.

For physical-PC evaluation, sign in as a genuine non-administrator Windows user and run both the installer and validator with **no UAC or elevation**. Any UAC prompt, unexpected service/WinDivert/system-proxy change, invalid package digest, failed SOCKS5/HTTPS result, or leaked `ciadpi` process is a **FAIL**. Keep the draft unpublished until *both* hosted and physical-PC gates pass. Do not disable security checks to get a green result.

## Hosted Windows launcher: 1,024-character command-line limit (2026-11-11)

Hosted run [42946553039](https://github.com/DarrenDorr/NetPilot/actions/runs/42946553039) failed before the test-user validator started: `CreateProcessWithTokenW` returned `0x80070057` (invalid argument). The prior `-EncodedCommand` approach passed the full PowerShell runner through a command line exceeding the **1,024-character documented limit** for this Win32 API. This is a hosted runner launch defect, not proof of a ByeDPI runtime failure.

The hosted harness now materializes the runner as `NetPilot-StandardUser-Runner.ps1` inside its already protected test-pack directory. The exact temporary user's SID receives only RX for the file; Administrators and SYSTEM retain administrative access. The native launch uses the absolute PowerShell executable and a short `-File` argument; the native wrapper rejects command lines reaching the API limit. Path replacement/reparse-point checks and fail-closed ACL setup prevent execution if the runner staging is invalid. The temporary script and user are removed in existing cleanup.

No allowance is granted to use a shared writable script path or execute as the workflow's administrative token. The hosted workflow **must run again and pass all existing standard-user, package identity, network, isolation and cleanup checks**, not just process creation, before review for production admission. `PRODUCTION_ADMISSION=BLOCK` remains unchanged.

## Physical-PC finding: primary HTTPS proxy error (2026-11-11)

A genuine non-elevated Windows user produced the following partial evidence: exact candidate, loopback listener, process owner, direct HTTPS (HTTP 200), and final service/proxy/WinDivert cleanup were all PASS; the first HTTPS-over-SOCKS5 request failed with a generic `HttpRequestException`. That report alone cannot distinguish TLS, SOCKS5 destination connect, DNS, transient network conditions or strategy incompatibility. The existing primary `byedpi-windows-recommended` profile remains unchanged pending targeted evidence.

The validator now records bounded **exception type + HRESULT + `HttpRequestError`/`SocketErrorCode` chains only** (no exception messages, stack traces, domains, IP addresses or credentials), together with per-probe elapsed time. On primary failure it compares the existing `byedpi-auto-tlsrec` profile using the same hash-verified, user-mode, loopback-only launcher with Job Object containment and owner checks. It records `DIAGNOSTIC_ALT_*` but **still returns FAIL even if the alternate succeeds**. This is diagnosis, never auto-fallback or release admission. `PRODUCTION_ADMISSION=BLOCK` remains in force until all mandatory checks pass and physical-PC evidence is reviewed.
